# AI 工厂 Intake 与产品理解机制

## 记忆类型

- domain: product
- status: draft

## 来源

- 原始想法：从 Phase 1.1 流程稳定化后，选择一个真实但不进入产品开发的想法来验证 AI 工厂流程。
- 外部引用：无。
- 对话上下文：用户希望先稳定流程，不急于开发产品功能；真正功能开发的前置条件是 AI 已充分消化用户想法，需求文档和 UI 设计图趋于完善。

## AI 当前理解

这个想法的核心不是做一个具体业务功能，而是建立 AI 工厂的“入口机制”：当用户提出原始想法、外部资料或阶段判断时，AI 工厂可以先接收、整理、澄清，并产出可确认的产品理解草案。

它要解决的问题是：AI 不能直接把用户想法变成开发任务，也不能凭一次对话就写 PRD。AI 需要先证明自己理解了用户的目标、问题、约束和价值，再等待用户确认。确认之后，才可以进入需求点记录、PRD、设计 brief 或工程规格。

这个机制是 AI 原生软件工厂的第一道“生产线入口”。它决定后续所有需求、设计和开发是否有可靠来源。

## 已确认事实

- Phase 1.1 的定位是流程稳定化，不做正式产品功能开发。
- Phase 1.2 才开始生成 PRD、产品理解成型、UI 设计图和设计资产。
- Phase 2 才进入受控产品开发。
- AI 可以主动生成理解和推荐方案，但必须等待用户确认。
- 用户允许 AI 补充推荐方案，但保留继续补充和修正的权利。
- 普通需求需要进入需求点记录，不进入 ADR。
- durable memory 必须由 AI 提出候选，再由用户确认。
- AI Factory Intake 方向准确，应该补充 Intake 分类。
- 用户允许下一步进入 `requirement-capture`。
- 用户确认需求陈述正确。
- Intake 分类需要增加“竞品观察”和“用户反馈”。
- 该需求不进入 PRD 候选池，作为 AI 工厂流程基础设施继续沉淀。

## 推测

- 用户希望未来每个产品想法都先经过 Intake，而不是直接进入规格或开发。
- 用户可能需要一个稳定的“想法收集箱”，用于放置对话、外部引用、竞品观察和临时灵感。
- 用户可能希望 AI 工厂能在多个来源之间建立联系，但不希望自动写入长期记忆。
- 这个机制未来可能会在 Admin 工作台中可视化，但 Phase 1.1 只需要流程和文档资产。

## Intake 分类建议

Phase 1.1 建议先采用以下分类，后续根据真实使用再调整：

| 分类      | 用途                                       | 进入后的下一步                       |
| --------- | ------------------------------------------ | ------------------------------------ |
| 产品想法  | 产品能力、用户场景、价值主张               | 进入产品理解与需求点记录             |
| 技术想法  | 架构、工具链、运行时、工程能力             | 进入工程规格或 ADR 候选              |
| 设计想法  | UI、体验、信息架构、设计系统               | 进入 design brief 候选               |
| 流程改进  | 工作流、Playbook、Prompt、Memory、同步规则 | 进入流程审计或 playbook 更新         |
| 外部引用  | 文章、截图、文档、访谈材料                 | 进入 intake 摘要，等待判断用途       |
| 竞品观察  | 竞品能力、竞品流程、竞品体验、市场表达     | 进入产品理解或设计/策略判断          |
| 用户反馈  | 用户需求、抱怨、访谈反馈、使用过程中的信号 | 进入需求点记录或产品理解             |
| 风险/问题 | 缺陷、矛盾、未知风险、流程不稳定点         | 进入 bugfix、review 或 process-audit |

每条 Intake 建议至少记录：

- id
- category
- source
- created
- status
- summary
- next workflow

## 待确认问题

- 这个 Intake 机制是否只服务当前项目，还是未来要作为通用 AI 工厂能力复用？
- 用户是否希望每条原始想法都有唯一 id 和状态？
- 外部引用进入 Intake 时，是否需要固定记录来源、日期、可信度和使用目的？
- 产品理解草案是否需要固定分为“已确认事实 / 推测 / 待确认问题 / 推荐方案 / 不进入执行的提醒”？

## 推荐方案

我建议把这个想法命名为：

```text
AI Factory Intake：想法到产品理解入口
```

Phase 1.1 只定义流程，不做产品功能：

1. 原始想法进入 `ai-factory/specs/intake/`。
2. AI 使用 `idea-to-product-understanding` 生成产品理解草案。
3. 草案进入 `ai-factory/specs/product-understanding/`。
4. 用户确认、补充或修正。
5. 确认后再决定是否进入 `requirement-capture`。
6. 阶段结束时通过 `memory-review` 判断是否有 durable memory 候选。

短期不做：

- 不做 Admin UI。
- 不做自动 intake 数据库。
- 不做自动生成 PRD。
- 不做自动进入需求点记录。
