# AI Engineering Code｜AI 原生软件工厂

## 一句话介绍

这是一个从零搭建的 AI 原生软件工厂 monorepo。它不是单纯的前端项目，也不是只接一个大模型接口的 Demo，而是把规格、记忆、工作流、契约、设计系统和运行时代码放在同一套可演进工程体系里。

## 项目要解决的问题

传统软件项目通常把需求、设计、上下文、提示词和架构决策散落在聊天记录、文档平台和代码之外。AI 参与开发后，这种散落会进一步放大：上下文丢失、提示词复制、服务过早拆分、契约漂移、设计系统无法复用。

本项目的核心目标是建立一套 AI 也能稳定理解和协作的工程结构。

## 当前已经完成

- 建立 TypeScript 与 Python 双生态 monorepo。
- 使用 pnpm workspace、Turborepo、Next.js、FastAPI 构建最小可运行基础。
- 把 `ai-factory/` 作为一等基础设施，管理规格、记忆、提示词、工作流、设计系统和 playbook。
- 建立 `contracts/` 作为跨运行时契约层。
- 实现 `/factory/status` 到 Admin 面板的第一条端到端薄切片。
- 建立中文文档、中文 Conventional Commits、Obsidian 阶段记录和飞书展示知识库。
- 运行第一条正式产品流程，产出 AI 时间管理 Agent 的产品理解、需求点、PRD、Design Brief 和 UI 设计图草案。

## 和普通项目的不同点

| 维度       | 普通项目             | 本项目                               |
| ---------- | -------------------- | ------------------------------------ |
| AI 上下文  | 临时聊天与零散提示词 | 结构化规格、记忆、工作流和提示词目录 |
| 架构演进   | 依赖个人记忆         | ADR、约定文档和阶段记录              |
| 前后端协作 | 手写接口和重复 fetch | OpenAPI、shared-types 和 SDK 边界    |
| 服务拆分   | 容易过早微服务化     | 先做模块边界，满足压力后再抽取运行时 |
| 展示方式   | 只有代码仓库         | GitHub、Obsidian、飞书三层证据链     |

## 适合面试展开的主题

- 为什么 AI 原生项目需要把 memory、spec、prompt、workflow 当作基础设施。
- 如何避免“AI 生成代码越多，仓库越不可维护”。
- 为什么早期使用模块边界，而不是直接拆微服务。
- 如何用契约和 SDK 减少前后端接口漂移。
- 如何通过阶段记录和 ADR 保留架构判断。

## 当前状态

项目处于 Phase 1.2 前期：AI 工厂流程已经能从想法逐步生成产品理解、需求点、PRD、Design Brief 和 UI 设计图草案。下一步重点不是马上写产品功能，而是先确认 UI 设计图，再进入工程规格阶段。
