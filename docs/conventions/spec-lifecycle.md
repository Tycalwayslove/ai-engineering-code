# 规格生命周期

## 目的

规格生命周期用于防止原始想法直接变成开发任务。AI 可以主动整理理解和推荐方案，但必须等待用户确认。

## 主链路

```text
原始想法
  -> AI 产品理解
  -> 用户确认 / 补充 / 修正
  -> 需求点记录
  -> PRD
  -> 工程规格
  -> 实施计划
```

## 阶段职责

| 阶段       | 位置                                      | 职责                                     |
| ---------- | ----------------------------------------- | ---------------------------------------- |
| 原始想法   | `ai-factory/specs/intake/`                | 保存未经整理的想法、外部资料和上下文入口 |
| 产品理解   | `ai-factory/specs/product-understanding/` | 记录 AI 对产品目标、用户和问题的理解     |
| 需求点记录 | `ai-factory/specs/requirements/`          | 保存普通需求点、确认状态和 PRD 候选      |
| PRD        | `ai-factory/specs/prd/`                   | Phase 1.2 生成正式产品需求               |
| 工程规格   | `ai-factory/specs/engineering/`           | 将已确认 PRD 转成工程边界                |
| 实施计划   | `ai-factory/specs/active/`                | 将工程规格转成可执行计划                 |

## 确认规则

- AI 可以主动生成产品理解，但不得默认进入 PRD 或开发。
- 产品理解必须标注：已确认、推测、待确认、推荐方案。
- 用户可以多轮补充；未确认内容不能成为开发任务。
- 普通需求不写入 ADR，而是进入需求点记录。
- ADR 只记录长期架构、流程、技术路线、权威来源和运行时边界判断。

## 流程实例规则

- 流程不按“对话次数”划分，而按“目标连续性”划分。
- 一个原始想法对应一个主流程实例；从 Intake、产品理解、需求点、PRD、设计 brief、UI 设计图到工程规格的多轮修改，都属于同一主流程实例。
- 同一目标下的补充、修正、评审、调试和版本迭代，应记录为同一流程实例的 revision 或状态轨迹，不新开无关流程。
- 只有目标改变、范围结构性扩大、产生独立可执行子方向，或旧流程已经关闭后重新启动时，才创建新流程或子流程。
- 子流程必须链接回主流程，说明它继承的目标、输入来源和决策边界。

## 归档规则

- 已完成、取消或被替代的规格移入 `ai-factory/specs/archived/`。
- 可长期指导决策的事实进入 durable memory 候选。
- 归档时必须保留原始来源和最终状态。
