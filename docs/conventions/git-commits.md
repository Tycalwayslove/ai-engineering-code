# Git 提交

## 目的

- 让提交历史对中文协作者更容易阅读。
- 保持社区通用 Conventional Commits 结构，方便后续自动化生成变更日志或版本信息。
- 让每个提交都表达清楚“改了什么”和“为什么值得独立记录”。

## 格式

提交标题使用：

```text
<type>(<scope>): <中文摘要>
```

`scope` 可省略：

```text
<type>: <中文摘要>
```

正文和 footer 默认使用中文。需要兼容工具识别的关键字保留英文，例如 `BREAKING CHANGE:`。

## 类型

- `feat`：新增用户可见能力、运行时能力或重要工作流能力。
- `fix`：修复缺陷、错误行为或破坏性遗漏。
- `docs`：只修改文档、说明、记忆或 Obsidian 相关规则。
- `style`：不影响语义的格式调整。
- `refactor`：不改变外部行为的代码结构调整。
- `test`：新增或修改测试。
- `chore`：维护性改动，例如依赖、脚本、仓库整理。
- `ci`：持续集成配置。
- `build`：构建系统或打包相关改动。
- `perf`：性能优化。
- `revert`：回滚提交。

## 规则

- 摘要使用中文，短句即可，不加句号。
- 摘要描述结果，不写泛泛的“更新代码”。
- 一个提交只表达一个阶段性变化。
- scope 使用稳定边界名，例如 `backend`、`sdk`、`contracts`、`ai-factory`、`conventions`。
- 已推送到远端的提交历史默认不改写；只有明确需要整理历史时，才通过受控 rebase 或 force push 处理。
- 阶段性结果提交后，如果影响项目理解，应同步写入 Obsidian 阶段成果记录。

## 示例

```text
docs(conventions): 记录中文提交规范
feat(factory): 增加工厂状态端到端闭环
ci(contracts): 在流水线中加入契约校验
fix(sdk): 规范化 API base URL
docs(ai-factory): 补充规格到实施计划工作流
```

## 演进

- 当提交类型不足以表达常见变化时，先在这里补充规则。
- 当需要自动生成变更日志或版本发布时，优先沿用该格式，不另建一套提交规范。
